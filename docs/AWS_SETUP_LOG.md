\# ASCOS — AWS Account Setup Log



This documents the manual, one-time AWS account setup done \*before\* any

Terraform was run. This isn't part of the Terraform codebase (nothing here

is code) — it's the human/console setup that had to happen first, so that

Terraform would have an account and identity to work with at all.



Recorded here so future-me (or anyone auditing the account) can see exactly

what was done, in what order, and why — same reasoning as every commit

note in `PROGRESS.md`, just for the parts that happened in a browser

instead of a text editor.

\## 1. AWS account created



\- Region confirmed as `ap-south-1` (Mumbai) — matches the project's frozen

&#x20; region decision, no changes needed.

\- Noted: AWS actually has two India regions — Mumbai (`ap-south-1`) and

&#x20; Hyderabad (`ap-south-2`, launched 2022). This project deliberately uses

&#x20; Mumbai only, per the master reference's frozen region decision; not

&#x20; using Hyderabad isn't a gap, it's a deliberate single-region choice.



\## 2. Root account MFA enabled



\- Root has unrestricted access to the entire account (billing, delete

&#x20; anything, remove users) — MFA here first, before touching anything else.

\- Chose \*\*Authenticator app\*\* over Passkey/security key. Reasoning:

&#x20; passkey is tied to one device/browser; authenticator app works from any

&#x20; computer via phone, which fits switching between machines (laptop,

&#x20; college lab, etc.) better than device-bound passkey sync.



\## 3. IAM user `vandana-admin` created



\- Created as a personal, day-to-day login — separate from root, so root

&#x20; is only used for account-level actions going forward (like this setup).

\- Permissions: `AdministratorAccess`, \*\*attached directly to the user\*\*,

&#x20; not via an IAM Group.

&#x20; - Considered a group (`infra-admins`) for easier future teammate

&#x20;   onboarding, since the master reference's `iam-team.tf` implies

&#x20;   multiple infra managers.

&#x20; - Decided against it for now: a group would give any future teammate

&#x20;   immediate full admin access the moment they're added, which isn't

&#x20;   something to hand out by default on a personal AWS account.

&#x20; - \*\*Deferred, not rejected\*\* — if a teammate (Nikhita/Rukkshana) needs

&#x20;   AWS access later and direct-attach makes onboarding them clunky,

&#x20;   revisit this and either create a scoped-down group/policy or decide

&#x20;   what specific access they actually need at that point.

\- Console password: custom, set directly (not autogenerated).



\## 4. MFA enabled on `vandana-admin`



\- Same reasoning as root — this is now the account used for actual daily

&#x20; work, so it needs the same protection.

\- Added as a second entry in the same authenticator app (distinct from

&#x20; the root entry).



\## 5. AWS CLI upgraded v1 → v2



\- Found existing installation was CLI v1 (`1.42.70`, installed \~1 year

&#x20; ago via pip, left over from a previous course project).

\- AWS CLI v1 entered maintenance mode on July 15, 2026 (critical

&#x20; fixes/security only, no new features or regions) and reaches full

&#x20; end-of-support July 15, 2027 — not dead yet, but clearly on the way out;

&#x20; current docs recommend migrating to v2 now rather than waiting.

\- Installed v2 via the official Windows MSI installer to `C:\\Program

&#x20; Files\\Amazon\\AWSCLIV2\\`.

\- Gotcha hit: an already-open Command Prompt window kept resolving to the

&#x20; old v1 (`...\\Python310\\Scripts\\aws`) because it had the pre-upgrade PATH

&#x20; cached in memory. Fixed by opening a \*\*new\*\* terminal window — v2

&#x20; resolved correctly there (`aws-cli/2.36.24`).

\- Old v1 install left in place (harmless, just unused now — v2 resolves

&#x20; first in a fresh terminal).



\## 6. CLI authentication — chose `aws login` over static access keys



\- Initial plan was a classic long-lived access key pair (`aws configure`

&#x20; with an Access Key ID / Secret Access Key).

\- Reconsidered after noticing AWS's own console warns against long-lived

&#x20; access keys, and current CLI docs (v2.32.0+) recommend `aws login`

&#x20; instead — a browser-based flow that reuses the existing console login

&#x20; and issues short-lived credentials (auto-expire, refresh up to a

&#x20; 12-hour session) instead of a permanent key sitting on disk.

\- Verified before committing to this: confirmed `aws login` genuinely

&#x20; requires no extra IAM permission for a user that already has

&#x20; `AdministratorAccess` (the `SignInLocalDevelopmentAccess` policy some

&#x20; guides mention is only needed for users \*without\* full admin — it

&#x20; grants exactly the two OAuth actions admin already includes via `\*`).

\- Also confirmed Terraform's AWS provider reads from the same shared

&#x20; credentials mechanism `aws login` writes to — no Terraform-specific

&#x20; changes needed to use this method.

\- Hit one snag: an old, dead access key from a previous (now-closed)

&#x20; AWS account/project was already sitting in

&#x20; `C:\\Users\\vanda\\.aws\\credentials`, blocking `aws login` from writing

&#x20; the new session (`Profile 'default' is already configured with Access

&#x20; Key credentials`). Cleared the file (old key belonged to an AWS account

&#x20; that no longer exists, so nothing lost) and retried successfully.

\- \*\*Result\*\*: authenticated as `vandana-admin` via `aws login`, confirmed

&#x20; with `aws sts get-caller-identity`:

&#x20; ```

&#x20; Account: 477554784986

&#x20; Arn:     arn:aws:iam::477554784986:user/vandana-admin

&#x20; ```

\- \*\*No permanent access key was created for this project.\*\* If a CLI

&#x20; session ever shows an auth error, the fix is just re-running

&#x20; `aws login` — no key rotation or secret management needed.

## 7. Terraform bootstrap completed

**What happened:** Terraform v1.15.9 was installed and initialized in
`terraform/bootstrap/`. The AWS provider (hashicorp/aws v5.100.0) was
downloaded and pinned via `.terraform.lock.hcl`.

**Why:** The bootstrap config exists to create the S3 bucket that will hold
Terraform's own remote state for the rest of the project — this can't live
in the remote backend it's creating, so it starts as local state.

**Problem:** Running `terraform plan` failed with "No valid credential
sources found." Investigation showed the AWS CLI session (via `aws login`)
had expired. After re-authenticating, a second issue appeared: `aws login`
refused to reinitialize the `default` profile because it was already
configured with `credential_process` credentials, causing a login loop.

**Solution:** Split authentication into two profiles:
- `ascos-login` — the profile refreshed daily via `aws login --profile ascos-login`,
  holding the real temporary session credentials.
- `ascos-terraform` — a profile whose `credential_process` reads from
  `ascos-login`, dedicated to Terraform's use.

The `provider "aws"` block in `main.tf` was updated to explicitly set
`profile = "ascos-terraform"`, so Terraform never depends on the `default`
profile.

**Verification:**
- `terraform plan` (before the fix) showed 5 resources to create, 0 changes,
  0 destroys — confirming the config itself was correct once auth worked.
- `terraform apply` completed successfully: **5 resources created** (S3
  bucket, versioning, server-side encryption, public access block, TLS-only
  bucket policy).
- A follow-up `terraform plan` (after the profile fix) returned:
  **"No changes. Your infrastructure matches the configuration."** —
  confirming the `ascos-terraform` profile chain works end-to-end.

**Result — real AWS resources now exist:**
- `state_bucket_name` = `ascos-dev-tfstate-477554784986`
- `state_bucket_arn` = `arn:aws:s3:::ascos-dev-tfstate-477554784986`
- `state_bucket_region` = `ap-south-1`

Bucket is versioned, AES256-encrypted, has Block Public Access fully enabled,
and denies any non-TLS access via bucket policy. `prevent_destroy` is set
in the resource lifecycle as a guardrail against accidental deletion.

**Note on credentials:** No access keys, session tokens, or credential
exports are recorded in this document — only profile names and the
authentication method. Session credentials are short-lived by design.

**What's next:** Bootstrap is complete. The next step is configuring the
root `terraform/backend.hcl` to point at this bucket, then running
`terraform init` in the root `terraform/` config to migrate onto the S3
remote backend.

## 11. Primary S3 storage design decided

The ASCOS primary application storage design was defined for Stage 3.

- Amazon S3 is the primary store for user-uploaded files.
- Files use the Cognito `sub` value as the stable application `user_id`.
- Per-user storage follows the convention `s3://<bucket>/{user_id}/...`.
- Hot storage maps to **S3 Standard**.
- Warm storage maps to **S3 Standard-IA**.
- Cold storage maps to **S3 Glacier Instant Retrieval**.
- S3 Block Public Access and server-side encryption will be enabled.
- Bucket versioning will be enabled.
- Lifecycle rules are limited to housekeeping and are not responsible for deciding Hot/Warm/Cold placement.
- ML-driven tier decisions will be handled by the future ASCOS optimization system rather than competing S3 lifecycle transitions.

## 13. DynamoDB data layer implemented

The ASCOS Stage 4 data layer was implemented as six separate DynamoDB tables, with keys derived from their required application, ML, and security access patterns:

| Table | Primary design | Purpose |
|---|---|---|
| `access_event` | `user_id` / `timestamp#event_id` + `user-file-index` GSI | Append-only access history and per-user/per-file ML features |
| `user_baseline` | `user_id` | Current per-user anomaly baseline and absolute activity counts |
| `protected_files` | `user_id` / `file_id` | Explicit user protection; row existence means protected |
| `predictions` | `prediction_id` + `user-file-index` + `user-index` GSIs | ML predictions, explanations, and recent user predictions |
| `feedback` | `feedback_event_id` + `prediction-index` GSI | Prediction feedback history and bandit context |
| `security_state` | `user_id` | Current per-user anomaly containment state |

- All six tables use **PAY_PER_REQUEST** billing for the project's small, variable initial workload.
- GSIs are limited to named operational access patterns; speculative and batch-analytics indexes are intentionally excluded.
- `co_access_signal` is computed from the user's chronological `access_event` stream rather than using a dedicated GSI unless later evaluation justifies one.
- `protected_files` blocks automated tier changes/bandit execution but does **not** stop access logging or ML observation/prediction.
- The tables provide the durable data foundation for later Lambda, ML, feedback, and security components; those processing components are not implemented by DynamoDB itself.
